# 1) Contexto e motivação (por que essa task existe)

Hoje o PRISMA faz o *matching* de **Opções Flex (OTC)** com dados do **AlphaTools (AT)** usando principalmente o **nome do ativo** como “chave” para correlacionar o que foi cadastrado via boleta vs o que vem do AT.

Na reunião, o time reforçou que:

* **match por nome nunca foi chave forte**, só foi “melhor esforço” que funcionou por um tempo;
* o **AlphaTools/XP muda o padrão de nome** (e mudou “de novo”), então a regra quebra sem controle do time;
* além disso, mesmo quando “encaixa”, ajustes (strike/PU/eventos corporativos) podem **descasar** cadastros já correlacionados.

✅ Objetivo: **tirar a dependência do “nome”** como base de match e evoluir para uma **chave forte** de contrato quando disponível.

# 3) Narrativa detalhada da reunião (o que foi discutido, passo a passo)

## 3.1 Ponto de partida: o match atual por nome não é confiável

O time explicou que a “chave forte” que se usa hoje é “na prática” o **nome** (acho que é um hardcoded no código tipo "sem barreira cadastrada"), mas:

* **nunca foi forte** (“nunca foi”);
* o nome já carregava características que mudam (quantidade, PU, strike…);
* e quando há evento corporativo (ex.: dividendo), **strike ajusta** e o nome deixa de ser constante.

Ou seja, mesmo no “padrão antigo” o nome já era instável; agora com mudanças recentes no padrão do AT, isso piorou.

**Conclusão técnica/negócio:**
Match por nome é **estruturalmente frágil** e exige manutenção constante.

---

## 3.2 Objetivo prático do encontro: entender como o PRISMA consulta o AT e achar um identificador forte

A conversa converge para a pergunta:

> “De que forma o PRISMA consulta isso no AlphaTools? Deve ser alguma API… se a gente achar um campo que seja chave forte, melhora a vida de todo mundo.”

Foi apresentado que existe no AT um campo candidato:

* **código/número do contrato** (chave forte)

A proposta foi:

* descobrir se esse campo aparece na **API** que o PRISMA usa (suspeita de “carteira”/posição),
* e, se aparecer, usar como base do match.

---

## 3.3 Demonstração em tempo real: telas do AT/PRISMA e o campo “Número do Contrato”

Durante a reunião, vocês foram para exemplos reais (COSAN / calls / datas) e confirmaram:

* No PRISMA, no detalhe da boleta, existe o campo **Número do Contrato**.
* Tentaram editar e salvar, mas existe trava do tipo “boletas linkadas com status” (ou necessidade de voltar status/editar via fluxo correto).
* Em paralelo, no AT existem contratos (em algumas linhas aparece “contrato”).

Isso virou o caminho:

1. **colocar/garantir o número do contrato** onde precisa (boleta/registro correto), e
2. fazer o PRISMA conseguir buscar e correlacionar esse contrato via API.

---

## 3.4 Descoberta crítica: em Opções Flex (OTC), “contrato” não é 1:1 como bolsa

Aqui foi a parte mais importante do debate técnico.

Vocês perceberam (na prática) que:

* uma mesma estrutura (mesmo ativo/strike etc.) pode ter **contratos diferentes** por cliente/contraparte;
* “Vale do Gaucho” e “Soulfuls” podem fechar “a mesma call” mas cada um gera **um número de contrato diferente**, porque OTC é **bipartite**.

Isso derruba um risco de modelagem:

* se o PRISMA tentar salvar “o contrato” como atributo único do “ativo”, vai “bugar”, porque não existe um único contrato para aquele “ativo” no sentido de bolsa.

✅ Conclusão:
O **número do contrato é chave forte**, mas precisa ser aplicado no **nível correto**:

* contrato/boleta/cliente/contraparte
  e não como “um contrato do ativo genérico”.

---

## 3.5 Alinhamento com Dev (William): o que o PRISMA faz hoje e qual é o passo 1 realista

Foi recapitulada a implementação atual:

* cadastro do ativo/registro vem **pela boleta**;
* a correlação (*matching*) atual é “por nome”.

E o encaminhamento ficou assim:

* verificar na **API** que abastece carteira/posição se o **código de contrato** vem;
* se vier, é a base do match “pra frente”;
* se não vier, não adianta “inventar regra” (ou tem que achar outra API / expor campo).

A motivação ficou explícita:

> “Se eu ficar criando regra de nome, amanhã eles mudam de novo.”

---

## 3.6 Caminho para legado (backfill): lote via planilha da clearing

Foi discutido que:

* existe volume grande (ex.: 120 contratos);
* mas há planilha que contém cliente, papel, quantidades, preço de exercício etc.;
* dá para gastar energia 1 dia e resolver “pra vida inteira” (fazendo match por múltiplos critérios e preenchendo o que faltar).

Esse backfill foi tratado como possível, mas dependente de alinhamento/priorização.

# 4) Decisões e encaminhamentos (saída objetiva da reunião)

### Decisão A — Evitar solução definitiva baseada em “padrão de nome”

Nome é fallback/histórico, não solução final.

### Decisão B — Confirmar disponibilidade do “código/número de contrato” na API que o PRISMA consome

* Se existe na API: implementar match por contrato.
* Se não existe: buscar outra API ou abrir demanda para expor o campo.

### Decisão C — Ajustar modelagem para OTC (contrato por contraparte/cliente)

Evitar “contrato no ativo único”; tratar contrato no nível correto.

### Decisão D — Considerar backfill do histórico em lote

Possível via planilha clearing + regras (cliente/papel/quantidade/strike etc.).

---

# 5) Escopo da task #3662 (proposto)

1. **Mapear** qual endpoint/API o PRISMA usa para carregar **carteira/posição/opções flex**.
2. **Validar** se o payload traz **código/número do contrato**.
3. **Implementar** match priorizando contrato (quando disponível).
4. **Garantir modelagem**: contrato associado ao nível certo (boleta/cliente/contraparte), sem colisão em casos multi-cliente.
5. **Fallback + observabilidade**: quando contrato não vier, manter fallback atual com log claro.

---

# 6) Critérios de aceite (bem práticos)

* [ ] Para Opções Flex com contrato disponível na API, o match ocorre **sem depender do nome**.
* [ ] Cenário real multi-cliente: “mesmas características” porém **contratos diferentes** não colidem e são exibidos/cadastrados corretamente.
* [ ] O PRISMA não tenta “forçar” 1 contrato por ativo genérico quando OTC exigir múltiplos.
* [ ] Logs/telemetria indicam quando caiu em fallback (ex.: “contrato ausente no payload”, “não encontrado no AT”, etc.).
* [ ] Validação com Middle Office (Diogo) e Consolidação (Cotrim) em pelo menos 1–2 exemplos reais.

---

# 7) Dependências / riscos

* Dependência: contrato precisa estar disponível no AT **via API** consumida pelo PRISMA (ou expor via integração).
* Risco: modelagem errada (contrato como atributo do ativo) quebra OTC.
* Risco: continuar “tunando nome” vira manutenção infinita.
