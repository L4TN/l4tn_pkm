	- ---# Documento de Especificação

**Especificação:** Migração das telas do Sistema de Consolidação (OutSystems) para módulo Angular no Prisma Frontend  
**Detalhes:**  
Migração das telas atuais do sistema de Consolidação, hoje implementadas em OutSystems, para um novo módulo em Angular dentro do Prisma Frontend.  
O backend existente, hoje exposto via projeto **Prisma External** (solução Prisma), será gradualmente centralizado no projeto **prismaService (EntryPoint)**, mantendo o mesmo domínio de negócio e comportamento funcional.

O escopo desta issue foca prioritariamente em **UI e camada de orquestração leve** (chamadas de API, validações de formulário e navegação), evitando alterar regras de negócio já consolidadas no backend, exceto pequenos ajustes necessários de compatibilidade.

**Área Demandante:** Consolidação / Controladoria (rotinas de fechamento e consolidação de posições)

## Escopo e Objetivo

**Objetivo Principal:**  
Migrar as telas atuais do módulo de Consolidação, hoje em OutSystems, para um novo módulo Angular dentro do Prisma Frontend, consumindo serviços a partir do projeto **prismaService (EntryPoint)**, garantindo a mesma capacidade funcional atual e preparando o terreno para evoluções futuras (desidratação de telas, melhoria de UX e desacoplamento de OutSystems).

**Contexto de Negócio:**  
O módulo de Consolidação é utilizado para visualização, parametrização e acompanhamento de posições consolidadas (carteiras, portfólios, instrumentos, boletas e relatórios).  
Hoje, a experiência do usuário é fragmentada entre OutSystems (UI) e Prisma (demais módulos). A migração para Angular:

- Alinha o módulo de Consolidação ao stack tecnológico padrão (Prisma Frontend + prismaService).
- Reduz dependência de OutSystems para o fluxo de consolidação.
- Facilita manutenção, auditoria e evolução das regras de negócio já centralizadas no backend.
- Abre caminho para desidratação de telas/funções e para uma visão mais modular (cadastros, boletas, relatórios, ranking).

## Análise de Oportunidades

**Valor Agregado:**

- Unificação da experiência do usuário no Prisma (elimina dependência visual de OutSystems).
- Redução de acoplamento entre UI e backend, usando Angular + APIs em prismaService.
- Facilitação de futuras refatorações (desidratação de telas e fluxos complexos).
- Melhoria de manutenibilidade e rastreabilidade (logs, versionamento, observabilidade).
- Possível redução de custos/licenciamento associados ao uso de OutSystems.

**Riscos Identificados:**

- Divergência comportamental entre a tela antiga (OutSystems) e o novo módulo Angular, caso o mapeamento não seja completo.
- Quebra de contratos entre Prisma External e prismaService se as APIs não forem alinhadas e versionadas corretamente.
- Risco de regressão em relatórios e cálculos de consolidação, se a camada de orquestração na UI for alterada além do necessário.
- Dependência de alinhamento com a equipe de negócio (Consolidação) para validar fluxos críticos (boletas, relatórios, ranking).

## Requisitos

### Requisitos Funcionais

1. **RF01 – Módulo de Consolidação em Angular:**  
   Implementar um novo módulo de Consolidação no Prisma Frontend (Angular), com navegação dedicada (menu/módulo próprio) que substitua o acesso atual via OutSystems.  
   - Critério: Usuário consegue acessar o módulo de Consolidação diretamente pelo menu do Prisma, sem precisar da UI OutSystems.  
   - Cenários de Teste:
     - Acesso ao módulo a partir do menu principal.
     - Redirecionamento correto conforme perfil/permissão.

2. **RF02 – Cadastros (Carteiras, Portfólios, Instrumentos):**  
   Disponibilizar telas de cadastro equivalentes às da solução atual (OutSystems), respeitando campos obrigatórios, validações e relacionamento entre entidades.  
   - Critério: Para um mesmo conjunto de dados, os cadastros criados/editados em Angular produzem o mesmo resultado no backend que as telas antigas.  
   - Cenários de Teste:
     - Inclusão, edição e consulta de carteiras.
     - Inclusão, edição e consulta de portfólios.
     - Inclusão, edição e consulta de instrumentos.

3. **RF03 – Boletas (Movimentos, Funções, Motor, Replicações e Recon):**  
   Implementar telas para lançamento, consulta e acompanhamento de boletas, utilizando os serviços do prismaService (EntryPoint) ou, provisoriamente, Prisma External onde necessário.  
   - Critério: Fluxo de lançamento e reconciliação de boletas deve funcionar de ponta a ponta sem perdas de funcionalidade em relação à solução atual.  
   - Cenários de Teste:
     - Criação de boleta.
     - Consulta e filtro por carteira/portfólio.
     - Execução de funções/motor de reconciliação.

4. **RF04 – Relatórios (Liberação, Processamento e Gráficos):**  
   Migrar telas de relatórios (liberação, processamento, painel com gráficos) mantendo parâmetros principais de filtro e layout mínimo necessário para operação.  
   - Critério: Relatórios gerados via novo módulo devem apresentar os mesmos resultados (dados) dos relatórios antigos.  
   - Cenários de Teste:
     - Geração de relatório com filtros simples.
     - Comparação de amostras entre relatório antigo (OutSystems) e novo.

5. **RF05 – Controle de Acesso e Perfis:**  
   Integrar o módulo de Consolidação ao modelo de permissões já existente no Prisma (menus/telas visíveis conforme perfil).  
   - Critério: Usuário sem permissão não consegue acessar o módulo ou determinadas telas sensíveis.  
   - Cenários de Teste:
     - Usuário com perfil Consolidação acessando todas as telas.
     - Usuário sem perfil tentando acessar URLs diretas do módulo.

### Requisitos Não-Funcionais

1. **RNF01 - Performance:**  
   - Tempo de carregamento inicial do módulo de Consolidação aceitável dentro do padrão do Prisma (ex.: < 3s em condições normais de rede interna).  

2. **RNF02 - Segurança:**  
   - Autenticação unificada com o Prisma (mesmo mecanismo atual).  
   - Respeito às permissões de backend (APIs prismaService/Prisma External com validação server-side).  

3. **RNF03 - Escalabilidade:**  
   - Uso de padrões e componentes Angular já utilizados no Prisma, permitindo reaproveitamento e evolução.  

4. **RNF04 - Manutenibilidade:**  
   - Código modular (módulo Angular isolado para Consolidação).  
   - Separação clara entre componentes de UI, serviços de API e modelos.  

5. **RNF05 - Observabilidade:**  
   - Logs estruturados para ações críticas (cadastro, boletas, relatórios).  
   - Possibilidade de correlacionar chamadas Angular → prismaService via IDs de correlação/traces quando disponível.

### Casos Edge e Tratamento de Erros

- **Cenário:** Falha na chamada de API ao prismaService/Prisma External.  
  - **Tratamento:** Exibir mensagem amigável (“Não foi possível carregar os dados. Tente novamente ou contate o suporte.”) e registrar log detalhado.  
  - **Comportamento Esperado:** Tela permanece utilizável; usuário pode tentar novamente ou mudar filtro.

- **Cenário:** Dados inconsistentes entre OutSystems e Prisma (fase de transição).  
  - **Tratamento:** Definir fonte de verdade (backend prismaService/Prisma External) e, se necessário, exibir aviso “Dados em processo de migração”.  
  - **Comportamento Esperado:** Não travar operação; registrar ocorrência para ajuste.

- **Cenário:** Usuário tentando acessar tela sem permissão.  
  - **Tratamento:** Bloqueio com mensagem “Acesso não autorizado”.  
  - **Comportamento Esperado:** Nenhum dado sensível é exibido.

## Solução Técnica

### Arquitetura

- **Frontend:**
  - Criação de um **módulo Angular de Consolidação** dentro do Prisma Frontend.
  - Utilização dos mesmos padrões de layout, componentes e serviços já adotados no Prisma.
  - Organização das telas em submódulos ou rotas (Cadastros, Boletas, Relatórios, Ranking).

- **Backend:**
  - Consumo prioritário de APIs expostas pelo **prismaService (EntryPoint)**.
  - Enquanto necessário, consumo de rotas do **Prisma External** para funcionalidades ainda não migradas, com plano de convergência posterior.
  - Manutenção das regras de negócio no backend; a UI Angular apenas orquestra fluxos e exibe dados.

- **Integração:**
  - Rotas REST (HTTP) consumidas via serviços Angular.
  - Padronização de modelos (DTOs) entre Angular e prismaService.
  - Mecanismo de tratamento de erros centralizado (interceptor Angular).

### Alternativas Consideradas

| Opção   | Prós                                               | Contras                                                | Motivo da Decisão                       |
| ------- | -------------------------------------------------- | ------------------------------------------------------ | --------------------------------------- |
| A - Manter UI em OutSystems e apenas ajustar backend         | Menor esforço imediato de UI                           | Mantém fragmentação tecnológica e de UX | Rejeitada                               |
| B - Criar novo módulo Angular consumindo prismaService       | Alinha com stack atual, melhora UX e manutenibilidade  | Maior esforço inicial de front + migração| **Escolhida**                           |
| C - Reescrever também regras de negócio no backend agora     | Padronização total imediata                            | Risco alto de regressão e escopo grande | Postergada (tratada em fases futuras)   |

### Design Patterns Aplicados

- Serviços Angular para encapsular chamadas de API.
- Componentização de telas em blocos reutilizáveis (listas, filtros, formulários).
- Eventual uso de Facade/Adapter no backend (prismaService) para compatibilizar contratos antigos de Prisma External.

### Componentes Afetados

- **Backend:**  
  - prismaService (EntryPoint) – novas APIs ou adaptação de existentes.  
  - Prisma External – consumo temporário e/ou desativação gradual de endpoints.

- **Frontend:**  
  - Prisma Frontend – inclusão de novo módulo de Consolidação, menus e rotas.  

- **Banco de Dados:**  
  - Tabelas existentes de Consolidação (sem alterações estruturais previstas nesta fase; foco na UI).  

- **Infraestrutura:**  
  - Ambientes já existentes de Prisma (DEV, HOM, PRD), com ajustes mínimos de deploy do frontend.

### Plano de Implementação

1. **Preparação**
   - Mapeamento completo das telas e fluxos atuais em OutSystems.
   - Identificação dos serviços hoje consumidos (Prisma External).
   - Definição das APIs alvo em prismaService (novas ou reutilizadas).
   - Criação da branch específica da issue 3365.

2. **Desenvolvimento**
   - Criação do módulo Angular de Consolidação no Prisma Frontend.
   - Implementação das telas de cadastro, boletas, relatórios e ranking (conforme tasks 1–11).
   - Integração com APIs prismaService/Prisma External.
   - Implementação de validações e mensagens de erro equivalentes às da solução atual.

3. **Validação**
   - Testes locais (desenvolvimento).
   - Homologação técnica (time Prisma).
   - Homologação funcional com a área de Consolidação, comparando comportamentos com a versão OutSystems.

4. **Entrega**
   - Code review e merge da branch.
   - Deploy em ambiente de staging/homologação.
   - Janela de corte definida para migração de uso (Orientar usuários a usarem apenas o novo módulo).
   - Monitoramento pós-deploy com acompanhamento de eventuais ajustes.

## Monitoramento Pós-Deploy

**Métricas de Sucesso:**

- Adoção do novo módulo (percentual de acessos via Prisma vs OutSystems).  
- Taxa de erros nas operações críticas (cadastros, boletas, relatórios).  
- Volume de chamados/incidentes relacionados à Consolidação após o go-live.

**Alertas e Observabilidade:**

- **Dashboards:**  
  - Monitorar erros de API relacionados a consolidação (4xx/5xx).  

- **Logs:**  
  - Logs estruturados com identificação de operação (cadastro, boleta, relatório).  

- **Traces:**  
  - Quando disponível, correlacionar fluxo UI → prismaService para identificar gargalos.

**Plano de Rollback:**  
- Em caso de falhas críticas, permitir retorno temporário ao uso da UI OutSystems enquanto os problemas são corrigidos.  
- Possibilidade de desabilitar o módulo Angular de Consolidação via configuração/flag, se necessário.

**Runbook:**

- **Sintomas de Problema:**  
  - Erros frequentes ao carregar telas de consolidação.  
  - Divergência de dados entre relatórios antigos e novos.  
  - Usuários incapazes de concluir fluxos de cadastros ou boletas.

- **Ações Imediatas:**  
  - Verificar logs e disponibilidade de APIs.  
  - Validar se o problema é de dados, permissão ou infraestrutura.  
  - Acionar time responsável (Prisma / Infra / Dados).

- **Escalação:**  
  - Escalar para Tech Lead e PO quando houver impacto direto em fechamento/rotinas críticas de consolidação.
