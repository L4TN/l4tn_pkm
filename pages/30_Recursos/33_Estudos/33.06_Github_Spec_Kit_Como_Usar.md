# GitHub Spec Kit — Guia Completo

> Guia unificado cobrindo conceito, instalação, fluxo completo, integração com Copilot/Claude e troubleshooting.

---

## 1. O Problema: Vibe Coding e o Caos

Quando você usa uma IA para codar sem estrutura, ela não tem "memória de projeto" — a cada prompt, ela começa quase do zero. Isso é o **Vibe Coding**: sair codando movido pela inspiração do momento.

### As 4 Armadilhas do Vibe Coding

| Armadilha | O que acontece |
|---|---|
| **Frankensteining** | Juntar partes de código de forma desorganizada, difícil de manter |
| **Perda de Contexto** | A IA esquece o que foi feito e sugere funcionalidades conflitantes |
| **Requisitos Ambíguos** | Incertezas se transformam em centenas de linhas de código inútil |
| **Refatoração Interminável** | Reconstruir a mesma funcionalidade 3, 4, 5 vezes |

---

## 2. A Solução: Spec-Driven Development (SDD)

SDD **inverte a lógica tradicional**: em vez de codar primeiro e documentar depois, você cria especificações que se tornam executáveis — o agente de IA usa essas especificações para gerar implementações.

O Spec Kit resolve isso criando **arquivos `.md` que viram a memória persistente do projeto** — a IA lê esses arquivos em cada comando e mantém o contexto do início ao fim.

| | Vibe Coding | SDD |
|---|---|---|
| **Começa com** | Código | Plano |
| **Plano** | Ambíguo | Claro e documentado |
| **Retrabalho** | Alto | Mínimo |
| **Contexto** | Perdido a cada iteração | Persistente em arquivos |

## 3. Instalação

> ⚠️ Tutoriais antigos mostram `npm install -g @github/spec-kit` — esse método está **descontinuado**. O Spec Kit migrou para Python/uv.

### Passo 1 — Instalar o `uv`

**Windows (PowerShell):**
```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

**Mac / Linux:**
```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

### Passo 2 — Instalar o Specify CLI

**Opção recomendada** — instalação persistente (use em qualquer projeto):
```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

**Opção rápida** — sem instalar, rode direto com `uvx`:
```bash
uvx --from git+https://github.com/github/spec-kit.git specify init meu-projeto
```

### Passo 3 — Inicializar o Projeto

```bash
# Novo projeto com Claude
specify init meu-projeto --ai claude

# Novo projeto com GitHub Copilot
specify init meu-projeto --ai copilot

# Dentro de uma pasta já existente
specify init --here --ai claude

# Windows com Copilot (PowerShell)
specify init --here --ai copilot --script ps

# Se o diretório já tiver arquivos
specify init --here --force --ai copilot

# Verificar se tá tudo certo
specify check
```

## 4. Estrutura de Diretórios e as 3 Camadas

Após o `specify init`, a seguinte estrutura é criada:

```
.github/
└── prompts/
    ├── speckit.constitution.prompt.md   ← comportamento do /constitution
    ├── speckit.specify.prompt.md        ← comportamento do /specify
    ├── speckit.plan.prompt.md           ← comportamento do /plan
    ├── speckit.tasks.prompt.md          ← comportamento do /tasks
    └── speckit.implement.prompt.md      ← comportamento do /implement

.specify/
├── memory/                              ← outputs salvos (a memória do projeto)
├── templates/                           ← templates internos de spec, plan, tasks
└── scripts/                             ← automações (git, branches, etc.)
```

### Camada 1: `.github/prompts/` — Templates dos Prompts

São os arquivos que o Copilot/Claude usa para montar o prompt enviado ao modelo quando você chama um slash command.

**O que contém:**
- Papel do agente naquele comando
- Instruções de como iterar com o usuário
- O que perguntar e o que gerar
- Onde salvar o resultado
- Referências a scripts de automação

**Você edita?** ✅ Sim — para personalizar o comportamento.

**Exemplo de personalização no `speckit.constitution.prompt.md`:**
```
# Adicione no início do arquivo:
IMPORTANTE: Não use arquivos existentes como base.
Faça perguntas uma por uma para elicitar os princípios do projeto.
```

### Camada 2: `.specify/memory/` — A Memória do Projeto

É onde os outputs de cada comando são salvos. É a memória persistente que os próximos comandos usam como contexto.

```
.specify/memory/
├── constitution.md   ← resultado do /constitution
├── spec.md           ← resultado do /specify
├── plan.md           ← resultado do /plan
└── tasks.md          ← resultado do /tasks
```

**Você edita?** ✅ Sim — refine os outputs gerados antes de avançar para o próximo passo.

### Camada 3: `.specify/scripts/` — Automação

Scripts bash/PowerShell que rodam internamente para criar branches Git, atualizar contexto e garantir consistência entre os artifacts.

**Você edita?** ❌ Raramente — só se tiver necessidade específica de infraestrutura.

### Tabela Resumo

| Pasta | O que é | Você edita? | Gerado por |
|---|---|---|---|
| `.github/prompts/` | Templates dos prompts enviados ao modelo | ✅ Para personalizar | `specify init` |
| `.specify/memory/` | Outputs dos comandos — memória do projeto | ✅ É o seu trabalho | Cada comando |
| `.specify/scripts/` | Automações Git e consistência de artifacts | ❌ Raramente | `specify init` |
| `.specify/templates/` | Templates internos de spec, plan e tasks | ✅ Para customizar formato | `specify init` |

## 5. Fluxo Completo de Comandos

```
/constitution → /specify → /plan → /tasks → /implement
                    ↓                  ↓
                /clarify           /analyze
```

| Comando | Pergunta respondida | Arquivo gerado |
|---|---|---|
| `/constitution` | Quais são as regras do projeto? | `constitution.md` |
| `/specify` | O quê e por quê construir? | `spec.md` |
| `/clarify` | Tem algo ambíguo na spec? | Atualiza `spec.md` |
| `/plan` | Como vai ser construído? | `plan.md` + artefatos |
| `/tasks` | Quais passos executar? | `tasks.md` |
| `/analyze` | Tudo está consistente? | Relatório de inconsistências |
| `/implement` | Bora codar! | Código-fonte |

### No Copilot (VS Code)

Os comandos são invocados como:
```
@workspace /speckit.constitution
@workspace /speckit.specify
@workspace /speckit.plan
@workspace /speckit.tasks
@workspace /speckit.implement
```

> ⚠️ O `@workspace` garante que o Copilot leia os arquivos do projeto.

**Pré-requisito:** Ativar Prompt Files no VS Code:
```json
// settings.json
{
  "chat.promptFiles": true
}
```

Abrir Copilot Chat em **Agent Mode**: `Ctrl+Shift+I`

## 6. Detalhamento de Cada Comando

### `/constitution` — Princípios do Projeto

**O que é:** A "constituição" do projeto — as regras não-negociáveis que guiam *todo* o desenvolvimento.

**Para que serve:** Definir princípios como:
- "Não usar testes nessa fase"
- "Preferir funções puras a classes"
- "Toda API deve ter tratamento de erro"
- "Stack obrigatória: TypeScript + React"

**Por que importa:** Todos os comandos seguintes respeitam a constituição. O `/analyze` verifica se o plano e as tasks *violam* o que foi definido aqui.

> Pense na constituição como o **arquiteto sênior invisível** que valida cada decisão do projeto.

**Exemplo de prompt:**
```
/speckit.constitution
Crie princípios focados em: qualidade de código, padrões de teste,
consistência de UX e requisitos de performance. Inclua governança
sobre como esses princípios guiam decisões técnicas.
```

**Forçar entrevista iterativa (em vez de geração direta):**
```
/speckit.constitution
Não use arquivos existentes como base. Faça perguntas
uma por uma para elicitar os princípios do projeto.
```

**Output:** `.specify/memory/constitution.md`

**Exemplo de conteúdo:**
```markdown
# Project Constitution v1.0.0

## Core Principles
1. **Simplicidade primeiro** — evitar over-engineering
2. **Testes obrigatórios** — cobertura mínima de 80%
3. **Performance** — respostas < 200ms para operações críticas

## Decision Guidelines
- Prefer native APIs over third-party libraries
- Mobile-first design for all UI components
```

### `/specify` — O Quê e o Porquê

**O que é:** Você descreve sua ideia em alto nível e a IA gera o `spec.md`.

**O que é gerado:**
- Histórias de usuário com critérios de aceite
- Seções **"Precisa de Esclarecimento"** com perguntas abertas
- Branch Git criada automaticamente (ex: `001-feature-name`)

**Dica de ouro:** Quanto mais detalhado for seu primeiro prompt aqui, melhor será toda a cadeia seguinte.

**Exemplo de prompt:**
```
/speckit.specify
Build a task management app called Taskify. Users can create projects,
add team members, assign tasks, and move tasks between Kanban columns
(To Do, In Progress, In Review, Done). Users can drag and drop cards
between columns. Cards assigned to the current user appear in a
different color. Users can add unlimited comments to cards.
Users can edit/delete only their own comments.
```

**Output:** `.specify/specs/001-taskify/spec.md`

**Exemplo de conteúdo:**
```markdown
# Feature Specification: Taskify

## User Stories

### US-001: Kanban Board Navigation
As a user, I want to view tasks organized in Kanban columns
so that I can track project progress at a glance.

**Acceptance Criteria:**
- [ ] Columns: To Do, In Progress, In Review, Done
- [ ] Cards display title, assignee, and priority
- [ ] Current user's cards are highlighted in blue
```

### `/clarify` — Resolver Ambiguidades *(opcional, mas recomendado)*

**Quando usar:** Logo depois do `/specify`, antes do `/plan`.

**O que faz:** Entra em modo "quiz" — a IA lê o `spec.md`, identifica ambiguidades e faz perguntas uma por uma.

**Exemplo de perguntas geradas:**
- "Como uma nova tarefa é adicionada — por botão ou atalho de teclado?"
- "Existe limite de caracteres no título?"
- "O que acontece quando uma tarefa vai para 'Concluído'?"

Cada resposta é **gravada no `spec.md`** com timestamp. Você pode pular e editar o `.md` manualmente.

---

### `/plan` — O Como (Stack Técnica)

**O que é:** Gera o plano técnico completo. **Aqui** você especifica a stack.

**O que é gerado:**

| Artefato | Para que serve |
|---|---|
| Plano de Implementação | Abordagem técnica detalhada |
| Modelo de Dados | Estrutura de dados e tipos (DNA da aplicação) |
| Contrato de API | Endpoints, requests e responses (acordo front/back) |
| Documento de Pesquisa | Justifica as decisões de arquitetura |

**Exemplo de prompt:**
```
/speckit.plan
Use Next.js 14 com App Router, TypeScript, Tailwind CSS.
Banco de dados: PostgreSQL com Prisma ORM.
API: REST com autenticação JWT.
Deploy: Vercel.
```

**Output:**
```
.specify/specs/001-taskify/
├── spec.md
├── plan.md           ← plano técnico detalhado
├── data-model.md     ← schema do banco
├── research.md       ← pesquisa sobre a stack
└── contracts/
    └── api-spec.json ← contratos da API
```

### `/tasks` — Plano de Ação

**O que é:** A IA lê **tudo** (spec + plan + modelo de dados) e gera o `tasks.md`.

**O que é gerado:**
- Tarefas organizadas por user story, ordenadas por dependência
- Marcadores `[P]` para tarefas paralelizáveis
- Caminhos exatos de arquivos para cada tarefa
- Checkpoints de validação por fase

**Exemplo de `tasks.md`:**
```markdown
# Implementation Tasks

## Phase 1: Database Setup
- [ ] Create Prisma schema (prisma/schema.prisma)
- [ ] Run initial migration
- [ ] Seed database with sample data

## Phase 2: API Layer [pode ser paralelo com Phase 3]
- [ ] [P] GET /api/projects — list all projects
- [ ] [P] POST /api/tasks — create task
- [ ] [P] PATCH /api/tasks/:id — update task status

## Phase 3: UI Components [P]
- [ ] KanbanBoard component (components/KanbanBoard.tsx)
- [ ] TaskCard component (components/TaskCard.tsx)
- [ ] DragAndDrop logic

### Checkpoint: Validate Kanban drag-and-drop before proceeding
```

> Cada tarefa **conhece o contexto das anteriores** — a tarefa 3 sabe o que foi decidido na tarefa 2.

---

### `/analyze` — Verificação de Consistência *(opcional, mas crítico)*

**Quando usar:** Depois do `/tasks`, antes de implementar.

**O que faz:** Varre os 3 arquivos principais (spec + plan + tasks) e verifica:
- Se estão **coerentes entre si**
- Se há **sub-especificações** (algo planejado mas não detalhado)
- Se alguma decisão **viola a constituição**

> ⚠️ Esse comando é **crítico** — é ele que evita surpresas durante a implementação.

---

### `/implement` — Executar a Implementação

**O que é:** A fase final. A IA lê o `tasks.md` e executa as tarefas uma por uma, gerando o código real.

**O que o agente faz:**
- Valida que constitution, spec, plan e tasks existem
- Executa tarefas respeitando dependências e paralelismo
- Roda comandos no terminal (npm install, prisma migrate, etc.)
- Se auto-corrige em caso de erros

> ⚠️ O agente vai rodar comandos locais no seu terminal. Certifique-se de ter as ferramentas necessárias instaladas (Node.js, Docker, etc.).

## 7. Comportamento por Modelo de IA

| Modelo | Comportamento padrão no `/constitution` |
|---|---|
| Grok Code Fast | Usa contexto disponível e gera direto |
| Claude Sonnet | Tende a perguntar iterativamente |
| GPT-4o | Híbrido — depende do contexto |

O prompt de cada comando tem lógica interna:
- Se houver contexto suficiente no repo → gera direto
- Se não houver contexto → entrevista iterativamente

## 9. Troubleshooting

**Slash commands não aparecem no Copilot:**
- Confirme que o VS Code foi aberto na raiz do repo (onde está o `.github/`)
- Confirme que `"chat.promptFiles": true` está no settings.json
- Confirme que está em Agent Mode (`Ctrl+Shift+I`)

**Agente gera direto sem perguntar:**
- Adicione no início do prompt: "Não use arquivos existentes como base. Faça perguntas uma por uma."
- Ou remova temporariamente arquivos com contexto do repo

**`specify init` falha na validação:**
- Use `--ignore-agent-tools` para pular verificação de CLI tools
- Use `--force` se o diretório já tiver arquivos
