# Pattern: Workspace Corporativo com Git Submodule + Dual Remote

**Data de criação:** 2026-03-01
**Autor:** Matheus Dias (L4TN)
**Tipo:** Pattern reutilizável
**Status:** Validado em produção (primeira aplicação: WHG/Prisma)

---

## Sumário

Este documento descreve um **pattern de infraestrutura Git** para separar contextos de trabalho corporativo do PKM pessoal, mantendo tudo conectado. O pattern resolve o problema de ter specs, tasks e notas de trabalho convivendo com organização pessoal em um único repositório, e prepara a estrutura para uso de **SDD (Spec-Driven Development)** com ferramentas como o **GitHub Spec Kit**.

O pattern é **replicável para qualquer empresa ou projeto**. Toda vez que entrar em uma nova empresa ou projeto, basta seguir este guia para montar a infraestrutura de trabalho.

---

## 1. O Problema que este Pattern Resolve

Quando se usa um PKM (Personal Knowledge Management) como repositório Git único para organizar toda a vida — pessoal, financeira, estudos, carreira e trabalho — surge um conflito:

- As **notas e specs de trabalho** precisam ser acessíveis de forma independente (para ferramentas de dev, para compartilhar com o time, para ter issues/PRs próprios)
- O **PKM** precisa manter a visão unificada de tudo (incluindo trabalho)
- Os **repos de código** do projeto precisam estar próximos das specs para o fluxo SDD funcionar
- Frequentemente existem **duas contas GitHub** envolvidas (pessoal + corporativa), cada uma com suas permissões

Sem este pattern, as specs ficam "presas" dentro do PKM pessoal, o fluxo SDD fica travado, e a separação entre vida pessoal e profissional fica comprometida.

---

## 2. Visão Geral do Pattern

O pattern consiste em 3 camadas:

```
CAMADA 1 - PKM (repo pessoal)
    └── Pasta de Trabalho/ → SUBMODULE apontando pro repo de specs

CAMADA 2 - Repo de Specs (repo independente)
    ├── Notas gerais da empresa
    ├── Notas de projetos/contratos
    ├── Sprints e tasks da empresa
    └── Sprints e tasks do projeto/sistema

    Configuração de remotes:
    ├── origin  → conta GitHub CORPORATIVA (uso diário)
    └── pessoal → conta GitHub PESSOAL (backup/sync)

CAMADA 3 - Repos de Código (um ou mais repos do projeto)
    ├── Frontend/ (.git)
    └── Backend/  (.git)
```

Todas as camadas ficam em `~/source/`, lado a lado:

```
~/source/
├── meu_pkm/           (Camada 1 - PKM com submodule)
├── empresa_specs/     (Camada 2 - clone independente das specs)
├── projeto_frontend/  (Camada 3 - código)
└── projeto_backend/   (Camada 3 - código)
```

## 3. Conceitos Fundamentais

### 3.1 Git Submodule

Um **submodule** é o mecanismo oficial do Git para incluir um repositório dentro de outro. O repositório pai (PKM) não armazena os arquivos do filho (specs) — armazena apenas uma **referência** (um ponteiro) dizendo "nesta pasta, use o repo X no commit Y".

**Analogia**: pense como um atalho inteligente. Quando você abre o PKM no explorador de arquivos, a pasta de trabalho está lá com todos os arquivos visíveis. Mas por baixo dos panos, é um clone de outro repo.

**Diferença de `git init` dentro de uma pasta:**

| Aspecto | `git init` (nested) | `git submodule add` |
|---------|---------------------|---------------------|
| Repo pai sabe que existe | Não | Sim (via `.gitmodules`) |
| Risco de conflito | Alto (`git add .` pode corromper) | Nenhum |
| Clone do pai traz o filho | Não (pasta vazia) | Sim (com `--recurse-submodules`) |
| Comandos dedicados | Nenhum | `git submodule status/update/init` |

### 3.2 Dual Remote (duas contas GitHub)

Um repositório local pode ter **múltiplos remotes**, cada um apontando para um repo diferente no GitHub. Isso permite manter o mesmo conteúdo em duas contas (pessoal e corporativa).

**Limitação no Windows**: o credential manager do Windows associa a autenticação HTTPS à conta ativa do `gh` CLI. Por isso, push simultâneo pra duas contas diferentes não funciona com URLs de push duplicadas no mesmo remote. A solução é ter **dois remotes separados**:

```
origin  → repo na conta CORPORATIVA (push padrão, uso diário)
pessoal → repo na conta PESSOAL (sincronização eventual)
```

Para fazer push no remote `pessoal`, é necessário trocar a conta ativa antes:

```bash
gh auth switch --user <conta-pessoal>
git push pessoal main
gh auth switch --user <conta-corporativa>  # volta pro padrão
```

### 3.3 Um repo pode ser clonado em vários lugares

Um repositório no GitHub pode ser clonado em quantas pastas quiser na mesma máquina. Todas as cópias fazem push/pull pro mesmo lugar. No pattern, o repo de specs existe em dois lugares:

- **Dentro do PKM** como submodule (para manter a visão unificada)
- **Em `~/source/`** como clone independente (para uso com ferramentas de dev)

### 3.4 Autenticação com múltiplas contas Git (Windows)

O `gh` CLI suporta múltiplas contas GitHub. O VS Code gerencia a autenticação via OAuth/HTTPS — quando você faz push, pode abrir uma janela pedindo pra escolher a conta.

Comandos úteis:

```bash
gh auth status                         # ver todas as contas logadas
gh auth switch --user <username>       # trocar conta ativa
gh auth login                          # adicionar nova conta
```

**Importante**: na máquina corporativa, deixar a conta da empresa como a ativa padrão. A conta pessoal só é ativada momentaneamente para sincronizar o remote `pessoal`.

## 4. Alternativas Consideradas (e por que foram descartadas)

Antes de adotar submodule, foram avaliadas outras opções:

**Opção A: `git init` dentro da pasta (repo nested)**
Rodar `git init` dentro da pasta de trabalho, criando um repo dentro do outro.
**Descartada**: o git do PKM não reconhece o repo interno. Pode gerar conflitos, e `git add .` no PKM pode corromper a relação.

**Opção B: `.gitignore` no PKM**
Criar o repo de specs dentro do PKM e ignorar a pasta via `.gitignore`.
**Descartada**: o PKM perde a referência. Quem clona o PKM não sabe que ali deveria ter algo.

**Opção C: Mover completamente pra fora do PKM**
Tirar a pasta de trabalho do PKM e colocar só em `~/source/`.
**Descartada**: o PKM fica incompleto. Perde-se a visão unificada.

**Opção D: Symlink**
Manter o repo em `~/source/` e criar um symlink dentro do PKM.
**Descartada**: frágil, pode quebrar entre máquinas ou SOs diferentes.

**Escolhida: Submodule** — combina o melhor de todas: PKM completo, repos independentes, sem conflitos.

## 5. Guia de Implementação (passo a passo genérico)

### Pré-requisitos

- `git` instalado
- `gh` CLI instalado e autenticado nas contas necessárias
- PKM já é um repo Git com remote no GitHub

### Variáveis do template

Substitua os valores abaixo pelos da sua situação:

```
CONTA_PESSOAL     = username da conta GitHub pessoal
CONTA_CORP        = username da conta GitHub corporativa
PKM_PATH          = caminho local do PKM (ex: ~/source/meu_pkm)
PASTA_TRABALHO    = caminho relativo da pasta de trabalho dentro do PKM
NOME_REPO         = nome do repo de specs (ex: whg, empresa-x, etc.)
NOME_CLONE        = nome da pasta do clone independente (ex: WHG, EmpresaX_Specs)
```

### Fase 1: Criar repos no GitHub

```bash
# Repo na conta pessoal
gh auth switch --user <CONTA_PESSOAL>
gh repo create <CONTA_PESSOAL>/<NOME_REPO> --private --description "Specs e Tasks - SDD"

# Repo na conta corporativa
gh auth switch --user <CONTA_CORP>
gh repo create <CONTA_CORP>/<NOME_REPO> --private --description "Specs e Tasks - SDD"
```

### Fase 2: Copiar conteúdo e fazer primeiro push

```bash
# Copiar conteúdo da pasta de trabalho para pasta temporária
mkdir ~/source/<NOME_REPO>_temp
xcopy "<PKM_PATH>\<PASTA_TRABALHO>\*" "~/source/<NOME_REPO>_temp\" /E /I /Q

# Inicializar git
cd ~/source/<NOME_REPO>_temp
git init
git add .
git commit -m "feat: importa conteudo de trabalho do PKM"

# Push pra conta pessoal (primeiro)
gh auth switch --user <CONTA_PESSOAL>
git remote add origin https://github.com/<CONTA_PESSOAL>/<NOME_REPO>.git
git branch -M main
git push -u origin main

# Adicionar remote corporativo e fazer push
git remote add corp https://github.com/<CONTA_CORP>/<NOME_REPO>.git
gh auth switch --user <CONTA_CORP>
git push corp main
```

### Fase 3: Converter para submodule no PKM

```bash
cd <PKM_PATH>

# Remover pasta do rastreamento do PKM
git rm -rf "<PASTA_TRABALHO>"
git commit -m "refactor: remove pasta de trabalho para migracao para submodule"

# Adicionar como submodule (usando o repo pessoal, já que o PKM é pessoal)
gh auth switch --user <CONTA_PESSOAL>
git submodule add https://github.com/<CONTA_PESSOAL>/<NOME_REPO>.git "<PASTA_TRABALHO>"
git commit -m "feat: adiciona specs como submodule"
git push
```

### Fase 4: Clone independente com dual remote

```bash
# Clone independente
cd ~/source
gh auth switch --user <CONTA_CORP>
git clone https://github.com/<CONTA_CORP>/<NOME_REPO>.git <NOME_CLONE>

# Configurar remotes
cd <NOME_CLONE>
# origin já aponta pro corporativo (uso diário)
# adicionar remote pessoal pra sync
git remote add pessoal https://github.com/<CONTA_PESSOAL>/<NOME_REPO>.git

# Verificar
git remote -v
# origin   https://github.com/<CONTA_CORP>/<NOME_REPO>.git (fetch)
# origin   https://github.com/<CONTA_CORP>/<NOME_REPO>.git (push)
# pessoal  https://github.com/<CONTA_PESSOAL>/<NOME_REPO>.git (fetch)
# pessoal  https://github.com/<CONTA_PESSOAL>/<NOME_REPO>.git (push)
```

### Fase 5: Limpar pasta temporária

```bash
rmdir /s /q ~/source/<NOME_REPO>_temp
```

## 6. Fluxo de Trabalho no Dia a Dia

### Editando specs (uso diário, conta corporativa)

```bash
cd ~/source/<NOME_CLONE>
# Editar arquivos...
git add .
git commit -m "spec: descricao da mudanca"
git push                    # vai pro repo corporativo automaticamente
```

### Sincronizando com o repo pessoal (eventual)

```bash
cd ~/source/<NOME_CLONE>
gh auth switch --user <CONTA_PESSOAL>
git push pessoal main
gh auth switch --user <CONTA_CORP>    # volta pro padrão
```

### Atualizando o submodule no PKM (eventual)

Quando quiser que o PKM reflita as mudanças mais recentes:

```bash
cd <PKM_PATH>
git submodule update --remote <PASTA_TRABALHO>
git add <PASTA_TRABALHO>
git commit -m "chore: atualiza submodule de specs"
git push
```

### Clonando o PKM em outra máquina (com specs)

```bash
git clone --recurse-submodules https://github.com/<CONTA_PESSOAL>/<PKM_REPO>.git
```

### Clonando só as specs

```bash
git clone https://github.com/<CONTA_CORP>/<NOME_REPO>.git
```

### Usando com Spec Kit (SDD)

O Spec Kit referencia:

- **Specs**: `~/source/<NOME_CLONE>/`
- **Código**: `~/source/<projeto>/`

## 7. Comandos de Referência

### Submodules

| Ação | Comando |
|------|---------|
| Ver status do submodule | `git submodule status` |
| Atualizar submodule pro último commit remoto | `git submodule update --remote` |
| Inicializar submodule após clone | `git submodule init && git submodule update` |
| Entrar no submodule e trabalhar | `cd <pasta-submodule> && git pull` |
| Clonar com todos submodules | `git clone --recurse-submodules <url>` |

### Múltiplas contas GitHub (gh CLI)

| Ação | Comando |
|------|---------|
| Ver contas logadas | `gh auth status` |
| Trocar conta ativa | `gh auth switch --user <username>` |
| Adicionar nova conta | `gh auth login` |
| Push pro remote secundário | `gh auth switch --user X && git push <remote> main && gh auth switch --user Y` |

### Múltiplos remotes

| Ação | Comando |
|------|---------|
| Ver todos os remotes | `git remote -v` |
| Adicionar remote | `git remote add <nome> <url>` |
| Renomear remote | `git remote rename <antigo> <novo>` |
| Alterar URL de um remote | `git remote set-url <nome> <nova-url>` |
| Push pra remote específico | `git push <nome> <branch>` |

## 8. Troubleshooting

### `index.lock: File exists`

**Causa**: processo git anterior não finalizou (VS Code, crash, etc.).
**Solução**: `del <repo>\.git\index.lock`

### `Repository not found` no push

**Causa**: a conta ativa do `gh` não tem acesso ao repo do outro remote.
**Solução**: trocar a conta ativa com `gh auth switch --user <conta-correta>` antes do push.

### Push dual (duas URLs no mesmo remote) não funciona no Windows

**Causa**: o credential manager do Windows usa a conta ativa do `gh` pra autenticação HTTPS. Ele não consegue alternar entre contas no mesmo comando.
**Solução**: usar dois remotes separados (`origin` e `pessoal`) e fazer push explícito pra cada um, trocando a conta antes.

### `local modifications` ao tentar `git rm`

**Causa**: arquivo modificado localmente que não foi commitado.
**Solução**: usar `git rm -rf` (force) em vez de `git rm -r`.

### VS Code mostra submodule como "modified" sem motivo

**Causa**: o submodule está em um commit diferente do que o PKM espera.
**Solução**: `cd <pasta-submodule> && git pull && cd .. && git add <pasta-submodule> && git commit -m "chore: atualiza submodule"`

## 10. Estrutura Final (template)

```
~/source/
├── <meu-pkm>/                               (repo git pessoal)
│   ├── .gitmodules                          (config dos submodules)
│   └── <pasta-trabalho>/                    (SUBMODULE → repo de specs)
│       ├── notas-empresa/
│       ├── notas-projetos/
│       ├── sprints-empresa/
│       └── sprints-projeto/
│
├── <specs-clone>/                           (clone independente)
│   ├── notas-empresa/                       remote origin  = conta corp
│   ├── notas-projetos/                      remote pessoal = conta pessoal
│   ├── sprints-empresa/
│   └── sprints-projeto/
│
└── <projeto>/                               (repos de código)
    ├── Frontend/ (.git)
    └── Backend/  (.git)
```

## 12. Lições Aprendidas

1. **Submodules são mais simples do que parecem**: na prática são 3-4 comandos no dia a dia. O conceito assusta, mas a execução é direta.

2. **Separação de contextos é poderosa**: specs de trabalho em repo próprio desacopla vida pessoal da profissional, sem perder a visão unificada no PKM.

3. **Push dual no Windows não funciona com HTTPS + múltiplas contas**: a solução é ter dois remotes separados e trocar a conta ativa antes do push pro remote secundário.

4. **Planejar antes de executar vale a pena**: avaliar alternativas (git init, .gitignore, mover fora, symlink, submodule) evita retrabalho.

5. **Sempre ter backup antes de operações destrutivas**: copiar o conteúdo para o novo repo ANTES de remover do PKM garante que nenhum arquivo é perdido.

6. **`index.lock` é comum e inofensivo**: quando o VS Code ou outro processo git trava, basta deletar `.git/index.lock`.

7. **Na máquina corporativa, a conta corp é a ativa padrão**: configurar o `origin` pra apontar pro repo corporativo simplifica o dia a dia. O repo pessoal vira remote secundário.

8. **O pattern é replicável**: toda vez que entrar em uma nova empresa, basta criar dois repos (pessoal + corp), adicionar submodule no PKM, clonar em `~/source/`, e configurar os remotes. A checklist da seção 9 guia todo o processo.
