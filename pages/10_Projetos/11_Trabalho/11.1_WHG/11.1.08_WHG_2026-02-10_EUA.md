## Plano Implementado: Captura de Requests de Entrada para Avaliação da Migração de FrontEnd

---

### Contexto e Necessidade

O FrontEnd do Prisma está passando por uma migração (versão antiga → versão nova). O Backend não muda — apenas o FrontEnd muda. Portanto, se ambos os FrontEnds enviarem **as mesmas requests** (mesmo path, mesmos parâmetros, mesma tipagem), o Backend retornará os mesmos resultados, e a migração é considerada segura.

O risco é que durante a reescrita do FrontEnd em TypeScript, dados, tipagem ou parâmetros de chamadas tenham sido alterados silenciosamente, gerando inconsistências.

### Requisitos

1. **Capturar requests de entrada** em um ponto central do Backend (não em cada controller individual)
2. **Dados a capturar por request:**
   - **Path** — a rota chamada (ex.: `/api/movimentacaoconta/get`)
   - **Request** — query params + body (os dados enviados pelo FrontEnd)
   - **Ambiente** — prd, uat ou dev
   - **Email do usuário** — para contextualizar quem fez a chamada
   - **Timestamp** — para correlacionar temporalmente
3. **Armazenar os logs em Azure Blob Storage**, organizados por ambiente (containers separados por env)
4. **Não impactar o funcionamento existente** — a captura é secundária e não pode afetar a performance nem quebrar requests
5. **Reaproveitar a infraestrutura existente** de blob logging (`InstrumentalizacaoBlobService`)
6. **Rotas configuráveis** — controlar quais rotas são capturadas via `appsettings`, sem necessidade de redeploy
7. **Habilitável/desabilitável** — poder ligar/desligar a captura sem alterar código

---

### O que precisa ser configurado

| Onde | O quê | Por quê |
|------|-------|---------|
| **Azure Portal** (Storage Account `whgsistemas`) | Criar manualmente 3 containers: `migracao-request-captura-prd`, `migracao-request-captura-uat`, `migracao-request-captura-dev` | O código **não cria containers automaticamente** — o `UploadFileStreamAsync` em `BlobService.cs` faz `GetBlobContainerClient` + `UploadAsync` diretamente. Se o container não existir, dará erro 404. |
| **appsettings.Common.json** | 1. `"MigracaoRequestCaptura": "migracao-request-captura"` na seção `AzureBlob.Containers` | O `BlobOptionsConfigure` lê essa seção e aplica o sufixo de env automaticamente |
| **appsettings.Common.json** | 2. Seção `"MigracaoRequestCaptura": { "Enabled": true, "Routes": [...] }` | Controla se a captura está ativa e quais rotas capturar |
| **Banco de dados** | **NÃO precisa** alterar nada | A `TbConfiguracao` com `EConfiguracao.AzureBlob` é um mecanismo de override em runtime, não um pré-requisito |

**Resumo: 3 containers no Azure Portal + appsettings. Sem alteração em banco.**

---

### Solução Técnica

Estender o `InstrumentalizacaoBlobService` existente com um novo método dedicado à captura de requests, chamado de forma centralizada pelo `ApplicationApiHandler` (ActionFilter). O método verifica se a captura está habilitada e se a rota está na lista de rotas configuráveis antes de gravar no blob.

---

### Lógica de implementação — Ordem e raciocínio

A implementação seguiu uma ordem de dependências **"de baixo para cima"** (infraestrutura → configuração → serviço → consumidor):

1. **Primeiro: Infraestrutura de config** (Steps 1-3) — Preparar o terreno para que o container exista como opção configurável
   - `BlobServiceOptions.cs` → propriedade para o nome do container
   - `AzureBlobCustomOptions.cs` → espelho da propriedade (padrão do projeto)
   - `appsettings.Common.json` → valor do container + configuração de rotas/enabled

2. **Segundo: Options de controle** (Steps 4-5) — Criar a classe que representa a configuração de captura e registrar no DI
   - `MigracaoRequestCapturaOptions.cs` → controle de `Enabled` e `Routes`
   - `MigracaoRequestCapturaOptionsConfigure.cs` → binding do appsettings via `BaseConfigureOptions<>` (auto-descoberto por reflection)

3. **Terceiro: Contrato** (Step 6) — Definir o método na interface antes de implementá-lo
   - `IInstrumentalizacaoBlobService.cs` → novo método `SendMigracaoRequestCapturaToBlobAsync`

4. **Quarto: Implementação** (Step 7) — O serviço que faz o trabalho real
   - `InstrumentalizacaoBlobService.cs` → injetar novos parâmetros, implementar o método com verificações de `Enabled`/`Routes` e upload ao blob

5. **Quinto: Consumidor/Chamador** (Step 8) — O ponto central que intercepta e chama o serviço
   - `ApplicationApiHandler.cs` → injetar o serviço e chamar fire-and-forget no `OnActionExecuting`

**Por que essa ordem?** Cada step depende do anterior estar pronto. O `ApplicationApiHandler` precisa da interface com o método. A interface precisa da classe de options. A implementação precisa do container configurado. Se fizéssemos na ordem inversa, teríamos erros de compilação em cada step.

### Step 5 — MigracaoRequestCapturaOptionsConfigure.cs (NOVO ARQUIVO) ✅

**Arquivo:** `Core/IoC/Configures/Services/MigracaoRequestCapturaOptionsConfigure.cs`

Classe de configuração que faz o binding do `appsettings.Common.json` → `MigracaoRequestCapturaOptions` via `IOptions<T>`. Segue o padrão do projeto: estende `BaseConfigureOptions<T>`, que é auto-descoberta por reflection no `ConfigureOptions()` do `DependencyInjectionExtencion.cs`.

```csharp
using IoC.Configures.Base;
using Microsoft.Extensions.Configuration;
using Services.Blob.Instrumentalizacao;

namespace IoC.Configures.Services;

internal class MigracaoRequestCapturaOptionsConfigure : BaseConfigureOptions<MigracaoRequestCapturaOptions>
{
    private readonly IConfiguration _configuration;

    public MigracaoRequestCapturaOptionsConfigure(IConfiguration configuration)
    {
        _configuration = configuration;
    }

    public override void Configure(MigracaoRequestCapturaOptions options)
    {
        _configuration.GetSection("MigracaoRequestCaptura").Bind(options);
    }
}
```

**Por que isso é necessário?** Sem essa classe, o `IOptions<MigracaoRequestCapturaOptions>` seria injetado com valores default (Enabled=true, Routes=[] → captura TUDO), ignorando o que está no appsettings. O `ConfigureOptions()` no DI auto-descobre via `Assembly.GetTypes().Where(t.IsSubclassOfGenericClass(typeof(BaseConfigureOptions<>)))` — não precisa alterar o `DependencyInjectionExtencion.cs`.

```csharp
public async Task SendMigracaoRequestCapturaToBlobAsync(
    string path, string queryString, object actionArguments,
    string userEmail, CancellationToken cancellationToken = default)
{
    // Guard 1: Captura desabilitada?
    if (!_migracaoOptions.Enabled)
        return;

    // Guard 2: Rota fora da lista?
    if (_migracaoOptions.Routes?.Count > 0)
    {
        string pathLower = path?.ToLower().Trim() ?? "";
        bool rotaEncontrada = _migracaoOptions.Routes.Any(r =>
            pathLower.Equals(r.ToLower().Trim(), StringComparison.OrdinalIgnoreCase));
        if (!rotaEncontrada)
            return;
    }

    try
    {
        string pathSanitizado = path?.Trim('/').Replace("/", "-").ToLower() ?? "unknown";
        string timestamp = DateTime.Now.ToString("yyyy-MM-ddTHH.mm.ss.fff");
        string blobFilePath = $"{DateTime.Now:yyyy/MM/dd}/{pathSanitizado}/{timestamp}.json";

        var jsonObject = new
        {
            Timestamp = DateTime.Now.ToString("yyyy-MM-ddTHH:mm:ss.fff"),
            Environment = _environment,
            Path = path,
            QueryString = queryString,
            UserEmail = userEmail,
            ActionArguments = actionArguments
        };

        string jsonContent = JsonConvert.SerializeObject(jsonObject,
            new JsonSerializerSettings { Formatting = Formatting.Indented });
        using var stream = new MemoryStream(Encoding.UTF8.GetBytes(jsonContent));
        await _whgBlobService.UploadFileStreamAsync(
            stream, _migracaoContainerName, blobFilePath, cancellationToken: cancellationToken);

        _logger.LogInformation(
            $"Captura de request '{blobFilePath}' gravada no container '{_migracaoContainerName}'.");
    }
    catch (Exception ex)
    {
        // NÃO propagar exceção — a captura de migração não deve quebrar a request
        _logger.LogError(ex,
            $"Erro ao gravar captura de request no blob {_migracaoContainerName}");
    }
}
```

**Diferença importante vs `SendServiceRequestToBlobAsync`:** o catch aqui NÃO faz `throw`. O método existente propaga a exceção. O novo método engole a exceção com log, pois a captura é secundária.
